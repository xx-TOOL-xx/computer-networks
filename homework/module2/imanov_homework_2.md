Система в контейнері «чиста», і команда `ss` спочатку не показувала жодного відкритого порту. Тому, як радить підказка до завдання, я запустив кілька мережевих служб:

```console
$ /usr/sbin/sshd                    # SSH-сервер, порт 22/tcp
$ nginx                             # вебсервер, порт 80/tcp
$ python3 -m http.server 8080 &     # простий HTTP-сервер, порт 8080/tcp
$ nc -u -l 5005 &                   # слухач UDP, порт 5005/udp
```

## Завдання 1. Аналіз відкритих портів

```console
$ ss -tuln
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
udp   UNCONN 0      0            0.0.0.0:5005      0.0.0.0:*          
tcp   LISTEN 0      5            0.0.0.0:8080      0.0.0.0:*          
tcp   LISTEN 0      128          0.0.0.0:22        0.0.0.0:*          
tcp   LISTEN 0      511          0.0.0.0:80        0.0.0.0:*          
tcp   LISTEN 0      128             [::]:22           [::]:*          
tcp   LISTEN 0      511             [::]:80           [::]:*          
```

Ключі команди: `-t` — TCP-сокети, `-u` — UDP-сокети, `-l` — лише ті, що очікують підключень, `-n` — показувати номери портів і адреси без перетворення на назви.

| Протокол | Порт | Служба | Стан |
| --- | --- | --- | --- |
| TCP | 22 | SSH (`sshd`) | LISTEN |
| TCP | 80 | HTTP (`nginx`) | LISTEN |
| TCP | 8080 | HTTP, навчальний сервер `python3 -m http.server` | LISTEN |
| UDP | 5005 | тестовий слухач `nc` | UNCONN |

Спостереження:

- TCP-сокети перебувають у стані `LISTEN`: служба відкрила порт і чекає на вхідні з'єднання.
- UDP-сокет має стан `UNCONN` (unconnected). UDP не встановлює з'єднань, тому стану «слухає» в нього немає: сокет просто прив'язаний до порту й приймає будь-які датаграми.
- Адреса `0.0.0.0` означає, що служба приймає підключення на всіх IPv4-інтерфейсах, а `[::]` — на всіх IPv6. Порти 22 і 80 відкриті для обох версій протоколу, тому трапляються у виводі двічі.
- Стовпець `Send-Q` для сокетів у стані `LISTEN` показує довжину черги з'єднань, що очікують прийняття (backlog): 128 у `sshd`, 511 у `nginx`, 5 у навчального сервера Python.

## Завдання 2. Аналіз процесів, що слухають порти

```console
$ ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess                           
udp   UNCONN 0      0            0.0.0.0:5005      0.0.0.0:*    users:(("nc",pid=3518,fd=3))     
tcp   LISTEN 0      5            0.0.0.0:8080      0.0.0.0:*    users:(("python3",pid=3517,fd=3))
tcp   LISTEN 0      128          0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=3504,fd=3))   
tcp   LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=3506,fd=5))  
tcp   LISTEN 0      128             [::]:22           [::]:*    users:(("sshd",pid=3504,fd=4))   
tcp   LISTEN 0      511             [::]:80           [::]:*    users:(("nginx",pid=3506,fd=6))  
```

Ключ `-p` додає стовпець `Process` з назвою процесу, його PID і номером файлового дескриптора сокета.

| Процес | PID | Порт | Протокол |
| --- | --- | --- | --- |
| `sshd` | 3504 | 22 | TCP |
| `nginx` | 3506 | 80 | TCP |
| `python3` | 3517 | 8080 | TCP |
| `nc` | 3518 | 5005 | UDP |

Назви процесів видно без `sudo`, бо в контейнері я працюю як `root`. Звичайному користувачеві `ss` показує лише його власні процеси, а для системних служб стовпець лишається порожнім — тоді команду треба запускати через `sudo`.

Один процес може тримати кілька сокетів: `sshd` (PID 3504) слухає порт 22 і на IPv4 (`fd=3`), і на IPv6 (`fd=4`).

## Завдання 3. Перевірка TCP-з'єднання

```console
$ nc -vz -w 5 google.com 80
Connection to google.com (142.250.109.139) 80 port [tcp/http] succeeded!
```

- Тип з'єднання: TCP
- Порт: 80 (`http`)
- Результат: з'єднання встановлено

Ключ `-z` наказує `nc` лише перевірити порт, не передаючи даних, `-v` — вивести докладне повідомлення, а `-w 5` обмежує очікування п'ятьма секундами. Перед підключенням `nc` звернувся до DNS і перетворив ім'я `google.com` на адресу `142.250.109.139` (вона показана в дужках).

Повідомлення `succeeded` означає, що відбулося тристороннє рукостискання TCP: клієнт надіслав `SYN`, сервер відповів `SYN-ACK`, клієнт підтвердив `ACK`. Отже, вузол досяжний, а на порту 80 справді працює служба, яка приймає з'єднання.

## Завдання 4. Порівняння TCP і UDP

```console
$ nc -vz -w 5 8.8.8.8 53
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
```

```console
$ nc -u -vz -w 5 8.8.8.8 53
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

Обидві команди повідомили про успіх, проте означає це різне. Щоб побачити різницю, я повторив обидві перевірки для порту 54, на якому сервер `8.8.8.8` нічого не обслуговує:

```console
$ nc -vz -w 4 8.8.8.8 54
nc: connect to 8.8.8.8 port 54 (tcp) timed out: Operation now in progress
```

```console
$ nc -u -vz -w 5 8.8.8.8 54
Connection to 8.8.8.8 54 port [udp/*] succeeded!
```

| | TCP | UDP |
| --- | --- | --- |
| Порт 53 (служба DNS працює) | `succeeded` | `succeeded` |
| Порт 54 (служби немає) | `timed out` — з'єднання не встановлено | `succeeded` — хоча там ніхто не слухає |
| Що насправді перевіряє `nc` | Чи завершилося рукостискання `SYN` → `SYN-ACK` → `ACK` | Лише те, що у відповідь не надійшло повідомлення про помилку |

Різниця в поведінці:

- **TCP** орієнтований на з'єднання. Перш ніж передавати дані, сторони встановлюють сесію, тому `succeeded` є справжнім підтвердженням від сервера. Якщо порт недоступний, `nc` про це дізнається: тут він не дочекався відповіді й завершився з помилкою.
- **UDP** працює без з'єднання. Датаграма просто надсилається, а підтвердження доставки протокол не передбачає. Тому `nc -u` вважає перевірку успішною, якщо не отримав ICMP-повідомлення «порт недосяжний», — і повідомив про «успіх» навіть для порту 54. Тобто `succeeded` для UDP не гарантує, що служба існує і датаграму отримано.

Висновок: TCP гарантує встановлення сесії, доставку й порядок даних ціною додаткових пакетів і затримки; UDP швидший і простіший, але надійність має забезпечувати сам застосунок. DNS використовує обидва: звичайні короткі запити йдуть по UDP, а TCP потрібен для великих відповідей і передачі зон.

## Завдання 5. DNS-резолвінг

Замість `google.com` я взяв домен `wikipedia.org`.

```console
$ dig wikipedia.org
; <<>> DiG 9.18.39-0ubuntu0.24.04.9-Ubuntu <<>> wikipedia.org
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 40095
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0
;; QUESTION SECTION:
;wikipedia.org.			IN	A
;; ANSWER SECTION:
wikipedia.org.		0	IN	A	185.15.59.224
;; Query time: 6 msec
;; SERVER: 192.168.65.7#53(192.168.65.7) (UDP)
;; WHEN: Wed Nov 18 20:56:36 UTC 2026
;; MSG SIZE  rcvd: 60
```

- Домен: `wikipedia.org`
- IP: `185.15.59.224` (запис типу `A` у секції `ANSWER SECTION`)
- DNS-сервер, який відповів: `192.168.65.7`, порт 53, по UDP (рядок `SERVER`)

Пояснення:

- `status: NOERROR` — запит оброблено без помилок; `ANSWER: 1` — у відповіді один запис.
- Прапорці `qr rd ra` означають: це відповідь (`qr`), клієнт просив рекурсивний пошук (`rd`), і сервер його підтримує (`ra`). Прапорця `aa` немає, тож відповідь неавторитетна: сервер не відповідає за зону `wikipedia.org`, а отримав дані від інших серверів або з кешу.
- `192.168.65.7` — це внутрішній DNS-резолвер Docker, адреса якого записана у файлі `/etc/resolv.conf` контейнера. Сам він записів не зберігає, а пересилає запити далі — DNS-серверу хоста й провайдера, які проходять ланцюжок від кореневих серверів до серверів зони `org` і зони `wikipedia.org`.
- Число у другому стовпці запису — TTL, час у секундах, протягом якого відповідь можна кешувати.
