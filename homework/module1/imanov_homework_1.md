У виводі є три групи інтерфейсів:

- `lo` — петльовий (loopback) інтерфейс з адресою `127.0.0.1/8`, через який система звертається сама до себе;
- `tunl0`, `gre0`, `sit0` та подібні — службові тунельні псевдоінтерфейси ядра; вони вимкнені (`state DOWN`) і не мають IP-адрес;
- `eth0` — єдиний інтерфейс, що з'єднує систему з мережею. Саме його розглядаю далі.

| Параметр | Значення | Пояснення |
| --- | --- | --- |
| Інтерфейс | `eth0` (у виводі `eth0@if26`) | Позначка `@if26` означає, що інтерфейс є одним кінцем віртуальної пари; другий кінець має індекс 26 і розташований на боці хоста |
| Тип підключення | Дротове Ethernet-з'єднання, віртуальне (`veth`) | Рядок `link/ether` вказує на Ethernet, а не Wi-Fi. Тип `veth` видно в детальному виводі нижче: це віртуальний «кабель» між контейнером і віртуальним комутатором (bridge) Docker |
| MAC-адреса | `b6:af:29:18:f3:a9` | Адреса канального рівня (L2). У першому октеті `b6` встановлено біт локального адміністрування, тобто адресу згенеровано програмно, а не «прошито» виробником мережевої карти |
| IP-адреса | `172.17.0.2` | **Мережевий рівень (L3) моделі OSI.** Приватна адреса з діапазону `172.16.0.0/12`, яка не маршрутизується в інтернеті |
| Маска | `/16`, тобто `255.255.0.0` | **Мережевий рівень (L3) моделі OSI.** Перші 16 біт адреси позначають мережу `172.17.0.0`, решта 16 біт — вузол у ній |
| Gateway | `172.17.0.1` | Шлюз за замовчуванням; його видно в таблиці маршрутів (завдання 2): `default via 172.17.0.1` |
| Broadcast | `172.17.255.255` | Поле `brd` у рядку `inet`: адреса, у якій усі біти вузла дорівнюють одиниці |
| Hosts | 65 534 | 2^16 − 2: з 65 536 адрес мережі віднімаємо адресу самої мережі (`172.17.0.0`) і широкомовну (`172.17.255.255`). Діапазон вузлів: `172.17.0.1` – `172.17.255.254` |

## Завдання 2. Дослідження маршрутизації

```console
$ ip r
default via 172.17.0.1 dev eth0 
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2 
```

У таблиці два маршрути:

1. `default via 172.17.0.1 dev eth0` — маршрут за замовчуванням. Усі пакети, адресовані за межі власної мережі, передаються шлюзу `172.17.0.1` через інтерфейс `eth0`.
2. `172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2` — маршрут до власної мережі. Вузли `172.17.0.0/16` доступні напряму, без шлюзу (`scope link`), а адресою відправника є `172.17.0.2`.

**Протокол, через який отримано IP.** У виводі немає позначки `proto dhcp`, тож адресу отримано **не через DHCP**. Вона призначена статично: під час створення контейнера Docker сам вибрав вільну адресу зі свого пулу (механізм IPAM) і записав її на інтерфейс. Позначка `proto kernel` у другому рядку означає, що цей маршрут ядро додало автоматично в момент призначення адреси інтерфейсу.

Для порівняння: на комп'ютері, під'єднаному до домашнього роутера, маршрут за замовчуванням зазвичай має вигляд `default via 192.168.1.1 dev wlp2s0 proto dhcp metric 600` — там `proto dhcp` показує, що адресу і шлюз видав DHCP-сервер роутера.

## Завдання 3. Знаходження публічної IP-адреси

```console
$ curl ifconfig.io
185.xxx.xxx.xxx
```

| | Адреса | Тип |
| --- | --- | --- |
| Локальна | `172.17.0.2` | приватна (RFC 1918) |
| Публічна | `185.xxx.xxx.xxx` | публічна, видана провайдером |

**Вони однакові?** Ні, адреси різні.

**Чому?** Локальна адреса `172.17.0.2` належить до приватного діапазону: такі адреси можна вільно використовувати всередині власних мереж, але в інтернеті вони не маршрутизуються. Щоб вузол із приватною адресою міг вийти назовні, на межі мережі працює NAT (трансляція мережевих адрес). Домашній роутер має два «обличчя»: у локальній мережі він є шлюзом із приватною адресою, а на зовнішньому (WAN) інтерфейсі має публічну адресу від провайдера. Коли пакет виходить в інтернет, роутер замінює в ньому приватну адресу відправника на свою публічну й запам'ятовує цю відповідність у таблиці трансляцій (разом із номером порту), а відповідь повертає тому вузлу, який надсилав запит.

Саме тому сервіс `ifconfig.io` бачить не мою локальну адресу, а публічну адресу роутера: для зовнішнього світу всі пристрої домашньої мережі виглядають як один вузол. У моєму випадку трансляція відбувається навіть двічі: спочатку Docker підміняє адресу контейнера адресою хоста, а потім домашній роутер — приватну адресу хоста публічною.

Такий підхід економить адреси IPv4 (одна публічна адреса на всю домашню мережу) і приховує внутрішню структуру мережі. Зворотний бік — до пристрою за NAT не можна під'єднатися ззовні напряму, для цього потрібне перенаправлення портів.
