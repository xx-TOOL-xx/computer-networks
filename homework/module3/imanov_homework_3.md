## Завдання 1. Аналіз HTTP-заголовків та статус-кодів

Для аналізу взяв сайт `wikipedia.org`. Ключ `-I` надсилає запит методом `HEAD`, тому сервер повертає лише заголовки без тіла сторінки.

```console
$ curl -sI http://wikipedia.org
HTTP/1.1 301 Moved Permanently
content-length: 0
location: https://wikipedia.org/
server: HAProxy
x-cache: cp3067 int
x-cache-status: int-tls
connection: close
```

- **Статус-код:** `301 Moved Permanently` — ресурс остаточно переміщено на іншу адресу. Клієнт має повторити запит за адресою із заголовка `Location`, а браузери й пошукові системи можуть запам'ятати нову адресу.
- **Location:** `https://wikipedia.org/`. Змінилася лише схема: `http` → `https`. Сервер примусово переводить відвідувача на захищене з'єднання, бо звичайний HTTP передає дані відкритим текстом. Тіла у відповіді немає (`content-length: 0`) — це суто службова відповідь-перенаправлення.
- **Версія протоколу:** `HTTP/1.1` (перший рядок відповіді).

Щоб побачити, чим закінчується ланцюжок, я звернувся вже по HTTPS:

```console
$ curl -sI https://www.wikipedia.org | head -12
HTTP/2 200 
date: Wed, 18 Nov 2026 18:20:53 GMT
cache-control: s-maxage=86400, must-revalidate, max-age=3600
server: ATS/9.2.16
etag: W/"1de8a-65fe76abb2e40"
last-modified: Tue, 10 Nov 2026 07:56:33 GMT
content-type: text/html
age: 11413
accept-ranges: bytes
x-cache: cp3066 miss, cp3066 hit/691391
x-cache-status: hit-front
strict-transport-security: max-age=106384710; includeSubDomains; preload
```

Тут статус `200` (запит успішний), а версія протоколу вже `HTTP/2`: під час встановлення TLS-з'єднання клієнт і сервер домовилися про новішу версію. Заголовок `strict-transport-security` (HSTS) наказує браузеру надалі звертатися до сайту лише по HTTPS, тож наступного разу перенаправлення `301` навіть не знадобиться. Заголовки `cache-control`, `age` і `x-cache-status: hit-front` показують, що відповідь віддав кеш-сервер, а не основний сервер.

## Завдання 2. Робота з методами HTTP

Тестовий API розгорнув локально: це невеликий сервер на Python зі сховищем у пам'яті — файл [`test_api.py`](test_api.py) поруч із цим звітом. Він слухає порт 8000 і підтримує `GET /tasks` та `POST /tasks`.

**Створення ресурсу (POST):**

```console
$ curl -si -X POST -H "Content-Type: application/json" -d '{"title": "Buy milk"}' http://localhost:8000/tasks
HTTP/1.1 201 Created
Server: BaseHTTP/0.6 Python/3.12.3
Date: Wed, 18 Nov 2026 21:31:06 GMT
Content-Type: application/json
Content-Length: 45
Location: /tasks/1

{"id": 1, "title": "Buy milk", "done": false}
```

- **Результат:** `201 Created` — ресурс успішно створено. Заголовок `Location: /tasks/1` повідомляє адресу нового ресурсу, а в тілі відповіді повертається сам створений об'єкт з `id`, який призначив сервер.

**Читання ресурсів (GET):**

```console
$ curl -si http://localhost:8000/tasks
HTTP/1.1 200 OK
Server: BaseHTTP/0.6 Python/3.12.3
Date: Wed, 18 Nov 2026 21:31:06 GMT
Content-Type: application/json
Content-Length: 47

[{"id": 1, "title": "Buy milk", "done": false}]
```

Тут статус `200 OK`: дані просто прочитано, нічого не створено. Якщо ж надіслати `POST` без обов'язкового поля, сервер відповідає `400 Bad Request`:

```console
$ curl -si -X POST -H "Content-Type: application/json" -d '{}' http://localhost:8000/tasks
HTTP/1.1 400 Bad Request
Server: BaseHTTP/0.6 Python/3.12.3
Date: Wed, 18 Nov 2026 21:31:06 GMT
Content-Type: application/json
Content-Length: 38

{"error": "Field 'title' is required"}
```

**Чим POST відрізняється від GET:**

| | GET | POST |
| --- | --- | --- |
| Призначення | Отримати дані | Надіслати дані на обробку, зазвичай створити ресурс |
| Де передаються дані | В адресі запиту — у шляху та параметрах після `?` | У тілі запиту; формат задає заголовок `Content-Type` |
| Вплив на стан сервера | Безпечний метод: не має нічого змінювати | Змінює стан: з'являється новий запис |
| Повторне виконання | Ідемпотентний: десять однакових запитів дають той самий результат | Неідемпотентний: кожен повтор створює ще один ресурс |
| Кешування | Відповіді кешуються браузером і проміжними серверами | За замовчуванням не кешується |
| Типовий код успіху | `200 OK` | `201 Created` |

Через те що параметри GET є частиною адреси, вони потрапляють в історію браузера, журнали серверів і заголовок `Referer`. Тому паролі та інші чутливі дані через GET передавати не можна. Дані POST в адресу не потрапляють, але «захищеними» їх робить не сам метод, а лише HTTPS. З неідемпотентністю POST пов'язане і знайоме попередження браузера «Надіслати форму повторно?» під час оновлення сторінки.

## Завдання 3. Перевірка TLS-сертифіката

Замість `google.com` перевірив `wikipedia.org`. Повний вивід `openssl s_client` дуже довгий (містить сам сертифікат у форматі PEM), тому я відфільтрував ключові рядки. Ключ `-servername` передає ім'я сайту в розширенні SNI, а `</dev/null` одразу закриває з'єднання після рукостискання.

```console
$ openssl s_client -connect wikipedia.org:443 -servername wikipedia.org </dev/null 2>/dev/null | grep -E "^(depth| *[0-9] s:| *i:|subject=|issuer=|New, |Server public key|Verification|Verify return code)"
 0 s:CN = *.wikipedia.org
   i:C = US, O = Let's Encrypt, CN = YE2
 1 s:C = US, O = Let's Encrypt, CN = YE2
   i:C = US, O = ISRG, CN = Root YE
 2 s:C = US, O = ISRG, CN = Root YE
   i:C = US, O = Internet Security Research Group, CN = ISRG Root X2
 3 s:C = US, O = Internet Security Research Group, CN = ISRG Root X2
   i:C = US, O = Internet Security Research Group, CN = ISRG Root X1
subject=CN = *.wikipedia.org
issuer=C = US, O = Let's Encrypt, CN = YE2
Verification: OK
New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256
Server public key is 256 bit
Verify return code: 0 (ok)
```

```console
$ openssl s_client -connect wikipedia.org:443 -servername wikipedia.org </dev/null 2>/dev/null | openssl x509 -noout -issuer -subject -dates
issuer=C = US, O = Let's Encrypt, CN = YE2
subject=CN = *.wikipedia.org
notBefore=Oct  4 18:34:51 2026 GMT
notAfter=Jan  2 18:34:50 2027 GMT
```

- **Хто видав сертифікат (Issuer):** `C = US, O = Let's Encrypt, CN = YE2` — проміжний центр сертифікації некомерційної організації Let's Encrypt.
- **Узгоджений протокол TLS:** `TLSv1.3`.
- **Обраний шифр (Cipher Suite):** `TLS_AES_128_GCM_SHA256`.

Пояснення:

- Сертифікат видано на ім'я `*.wikipedia.org` — це wildcard-сертифікат, дійсний для всіх піддоменів. Термін дії короткий, близько трьох місяців (`notBefore` – `notAfter`): Let's Encrypt видає сертифікати автоматично, і короткий термін зменшує шкоду в разі викрадення ключа.
- У виводі видно **ланцюжок довіри**: сертифікат сайту (0) підписано проміжним центром `YE2` (1), його — кореневим центром ISRG (2, 3). Браузер довіряє сайту, бо довіряє кореневому сертифікату, який зберігається в операційній системі. Рядок `Verify return code: 0 (ok)` підтверджує, що весь ланцюжок перевірено успішно.
- Шифр `TLS_AES_128_GCM_SHA256` означає: дані шифруються алгоритмом AES зі 128-бітним ключем у режимі GCM, який одночасно забезпечує і конфіденційність, і цілісність; SHA-256 використовується для виведення ключів. У TLS 1.3 у назві шифру вже немає алгоритму обміну ключами — він узгоджується окремо і завжди забезпечує пряму секретність (forward secrecy).
- `Server public key is 256 bit` — сервер використовує ключ на еліптичних кривих; 256 біт для них відповідають приблизно 3072 бітам RSA.

## Завдання 4. Аналіз безпеки Cookies

Сайт — `github.com`. Команда `curl -v` показує заголовки відповіді; я залишив лише рядок статусу та заголовки `Set-Cookie`. Значення двох cookie скоротив, бо це довгі випадкові рядки.

```console
$ curl -sv -o /dev/null https://github.com 2>&1 | grep -iE "^< (HTTP|set-cookie)"
< HTTP/2 200 
< set-cookie: _gh_sess=<скорочено>; path=/; HttpOnly; secure; SameSite=Lax
< set-cookie: _octo=<скорочено>; expires=Thu, 18 Nov 2027 21:31:07 GMT; domain=.github.com; path=/; secure; SameSite=Lax
< set-cookie: logged_in=no; expires=Thu, 18 Nov 2027 21:31:07 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

| Cookie | HttpOnly | Secure | SameSite | Термін дії |
| --- | --- | --- | --- | --- |
| `_gh_sess` | так | так | `Lax` | сесійна (без `expires`) — зникає після закриття браузера |
| `_octo` | **ні** | так | `Lax` | 1 рік |
| `logged_in` | так | так | `Lax` | 1 рік |

**Від якої атаки захищає `HttpOnly`.** Від викрадення cookie через міжсайтовий скриптинг (XSS). Cookie з цим атрибутом браузер надсилає на сервер, але не віддає JavaScript-коду сторінки: `document.cookie` її не покаже. Тож навіть якщо зловмисник зуміє вбудувати на сторінку свій скрипт, він не зможе прочитати ідентифікатор сесії та переслати його собі. Саме тому сесійна cookie `_gh_sess` має `HttpOnly`. Натомість `_octo` — ідентифікатор для аналітики, до якого має звертатися клієнтський скрипт, і цінності для викрадення сесії він не має, тому `HttpOnly` у нього немає. Важливо, що атрибут не усуває саму XSS-вразливість, а лише обмежує її наслідки.

**Роль атрибута `Secure`.** Cookie з цим атрибутом браузер передає лише захищеним з'єднанням HTTPS. Без нього cookie могла б «витекти» відкритим текстом під час випадкового звернення по HTTP — наприклад, у публічній мережі Wi-Fi, де трафік можна перехопити (атака «людина посередині»). У GitHub усі три cookie мають `Secure`.

**`SameSite=Lax`** доповнює захист: браузер не додає cookie до запитів, які ініціює сторонній сайт (форми, зображення, фонові запити), і надсилає її лише під час звичайного переходу за посиланням. Це захист від підробки міжсайтових запитів (CSRF).

## Завдання 5. Архітектурне моделювання

**Система:** онлайн-біржа, де ціни змінюються щосекунди, а внутрішні сервіси мають обмінюватися даними з мінімальною затримкою.

### Сценарій А. Оновлення графіків цін у браузері в реальному часі — WebSocket

Обираю **WebSocket** (поверх TLS, тобто `wss://`).

- У класичному HTTP ініціатором завжди є клієнт: щоб дізнатися нову ціну, браузер мав би щосекунди надсилати запит. Це тисячі зайвих запитів із повним набором заголовків, а дані однаково запізнюються на інтервал опитування.
- WebSocket встановлює одне постійне з'єднання (починається як HTTP-запит із заголовком `Upgrade`), після чого **сервер сам надсилає** нову ціну, щойно вона змінилась. Затримка мінімальна.
- Службові дані кожного повідомлення — лише кілька байтів, а не сотні, як у HTTP-заголовках. Для потоку дрібних частих оновлень це суттєво.
- Канал двосторонній: тим самим з'єднанням браузер повідомляє, на які акції підписатися чи від яких відписатися, коли користувач перемикає графіки.
- WebSocket підтримують усі сучасні браузери без додаткових бібліотек.

Альтернатива — Server-Sent Events: простіший варіант, коли дані йдуть лише від сервера до клієнта. Проте біржі потрібен і зворотний канал (підписки, а в перспективі й заявки), тому WebSocket підходить краще. REST-опитування та gRPC тут програють: перше через затримки й навантаження, друге — бо браузер не може працювати з gRPC напряму без проміжного проксі.

### Сценарій Б. Взаємодія внутрішніх мікросервісів (білінг ↔ облік акцій) — gRPC

Обираю **gRPC**.

- **Швидкість.** gRPC працює поверх HTTP/2 і передає дані у двійковому форматі Protocol Buffers. Повідомлення виходять у кілька разів компактнішими за JSON, а їх розбір потребує менше процесорного часу — це пряма економія на затримці.
- **Одне з'єднання для багатьох викликів.** Мультиплексування HTTP/2 дає змогу виконувати багато запитів паралельно в одному TCP-з'єднанні, не витрачаючи час на нові рукостискання.
- **Строгий контракт.** Інтерфейс сервісу описано у `.proto`-файлі, з якого генерується код клієнта й сервера для різних мов. У фінансовій системі це важливо: помилку в типі чи назві поля буде виявлено під час компіляції, а не тоді, коли гроші вже списано.
- **Потокова передача.** Якщо обліку потрібно безперервно передавати білінгу виконані угоди, gRPC підтримує потоки в обох напрямках.
- **Контроль затримок.** Вбудовані дедлайни й скасування викликів не дають одному «завислому» сервісу заблокувати весь ланцюжок.

Недоліки gRPC — двійкові повідомлення не прочитати «на око», а браузери не підтримують його напряму — у цьому сценарії не заважають: обидва сервіси внутрішні, і людина з ними напряму не взаємодіє. REST тут працював би, але повільніше й без гарантій контракту; WebSocket не дає типізованих викликів «запит — відповідь».

### Підсумок

| Сценарій | Протокол | Головна причина |
| --- | --- | --- |
| А. Графіки цін у браузері | WebSocket | Сервер сам надсилає оновлення постійним двостороннім з'єднанням, яке підтримують усі браузери |
| Б. Білінг ↔ облік акцій | gRPC | Найменша затримка та строгий типізований контракт між сервісами |

Обидва рішення доповнюють одне одного: усередині системи сервіси спілкуються через gRPC, а окремий шлюз перетворює внутрішні події про зміну цін на повідомлення WebSocket для браузерів.
